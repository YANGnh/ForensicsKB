# Umi-OCR 100 张分层试点报告

- 日期：2026-11-03
- 基线：`main` @ `eefcdd7`（工作区干净，未改 OCR、索引或检索逻辑）
- 目的：判断是否值得用本地 Umi-OCR Paddle 版重做 OCR，并量化收益与风险
- 结论先行：**中文 UI、聊天、表格、低质截图值得换用 Umi；代码/终端截图不建议单独换，需保留 tesseract 或做双引擎路由。**

## 1. 样本与方法

从全库 3,465 张有 OCR 的图片中抽取 **100 张**，覆盖 27 个文档、2024/2025/2026 三年（47/50/3），全部来自 `02-WriteUp`。按旧 OCR 文本与图片尺寸分层：

| 分层 | 数量 | 选取依据 |
|---|---:|---|
| chinese | 30 | 中文占比高、界面/聊天/正文为主 |
| code | 25 | 代码、命令、终端特征明显 |
| table | 20 | 表格、日志、时间/数字密集 |
| low_quality | 15 | 小图、低分辨率、旧 OCR 文本很少 |
| mixed | 10 | 中英混排、图文混排 |

> 分层依据包含旧 OCR 结果，存在“旧 OCR 越差越容易被归入低质层”的选择偏差；本报告看的是方向性收益，不是全库无偏估计。

对比对象：

- 旧：仓库现有 `ocr/*.txt`，tesseract 5.5.3 + `chi_sim+eng`，未重跑。
- 新：Umi-OCR 2.1.5，PaddleOCR 中文模型 `models/config_chinese.txt`，`limit_side_len=2880`，`tbpu.parser=multi_para`，`data.format=text`。
- 代码层额外跑英文模型 `models/config_en.txt` + `single_code`，仅用于观察英文空格恢复能力，不作为主方案。

指标均为代理指标：字符数、CJK 数、中文字间空格、ASCII 单词数、关键词命中图数；未做逐字 CER 标注，结论另做了人工抽样复核。

## 2. 总体结果

| 指标 | 旧 OCR | Umi | 变化 |
|---|---:|---:|---:|
| 总字符 | 60,391 | 70,647 | +17.0% |
| CJK 字符 | 1,912 | 6,740 | 3.53× |
| 中文字间空格 | 664 | 1 | 基本消失 |
| ASCII 单词 | 4,482 | 4,540 | +1.3% |

逐图看：74 张 CJK 增加、13 张持平、13 张下降；旧 OCR 有 3 张“无可用文本”，Umi 后为 0 张；旧 OCR 非空白字符 <20 的 2 张，Umi 后全部 >20。

Umi 100 张总耗时 **216.4 秒**，均值 **2.16 秒/张**，中位 **1.30 秒/张**，最大 18.53 秒。按中位估算全库 3,465 张约 **75 分钟**，按均值约 **125 分钟**（单并发）；2–4 并发可明显缩短，但需注意本地服务稳定性。

## 3. 分层明细

| 分层 | n | 字符（旧→新） | CJK（旧→新） | 中文空格（旧→新） | ASCII 单词（旧→新） |
|---|---:|---:|---:|---:|---:|
| chinese | 30 | 5,704 → 9,463 | 867 → 2,966 | 347 → 0 | 326 → 367 |
| code | 25 | 24,266 → 24,687 | 329 → 828 | 96 → 0 | 2,126 → 1,964 |
| table | 20 | 24,890 → 29,307 | 629 → 2,400 | 206 → 1 | 1,567 → 1,688 |
| low_quality | 15 | 2,326 → 2,484 | 55 → 216 | 9 → 0 | 199 → 201 |
| mixed | 10 | 3,205 → 4,706 | 32 → 330 | 6 → 0 | 264 → 320 |

几个典型改善：

- 龙信杯 UI 截图：18 → 289 CJK，菜单、账号、时间、文件名基本可读。
- 数证杯虚拟机截图：1 → 188 CJK。
- 美亚杯虚拟机截图：7 → 180 CJK。
- 盘古石 `b73692...jpg`：旧 OCR 为“无可用文本”，Umi 能读出网页正文、价格、按钮和弹窗提示。

表格层数字串从 478 增至 555，时间戳、文件名、账号、金额等实体明显更全；但 `multi_para` 的阅读顺序偶有错位，不能假设输出行序等于原始版面顺序。

## 4. 检索召回

对旧/新 OCR 均做 CJK 空格归一化后，统计包含关键词的图片数：

| 关键词 | 旧命中 | 新命中 |
|---|---:|---:|
| 取证 | 3 | 6 |
| 密码 | 1 | 9 |
| 数据库 | 0 | 4 |
| 时间 | 3 | 18 |
| 用户 | 1 | 15 |
| 文件 | 4 | 30 |
| 网络 | 1 | 8 |
| 微信 | 0 | 4 |
| 登录 | 1 | 6 |
| 服务器 | 2 | 8 |

“电子数据”“flag”两组仍为 0→0，说明样本中这两类内容本身很少，不能据此判断 Umi 对该类词无效。

这项收益不是单纯“去空格”带来的：旧 OCR 已做归一化，命中提升主要来自识别正确率。即便如此，`tools/search.ps1` 目前仍是逐行原始正则，重做 OCR 后必须同步做查询归一化，否则收益会被抵消。

## 5. 代码/终端截图的硬伤

Umi 中文模型会把英文 token 粘在一起：

```text
publicstaticbooleanb(Stringstr,Stringstr2)
importbcrypt
```

- 含 `public static` 的代码图从 2 张降到 1 张。
- code 层 ASCII 单词在 17/25 张下降、8 张上升，均值 85.0 → 78.6（-7.6%）。
- 最长连续 token 从 53 增至 66，说明“粘连”确实发生。
- token 计数：`public` 32→24、`static` 3→2、`Exception` 2→1、`FROM` 3→1；同时 `String` 0→2、`class` 8→11，说明 Umi 也识别出了旧 OCR 漏掉的代码结构，不能简单说“全面变差”。

英文模型能恢复空格（`public static boolean bString str...`），但中文全丢或乱码（`method bO?`），还会误识别引号、括号和数字。因此：

- 中文注释/说明文字：Umi 更好；
- 代码主体、命令、哈希、终端输出：tesseract 或英文模型更稳；
- 最稳妥的是按图片内容路由，而不是全库单引擎覆盖。

## 6. 结论与建议

**试点通过（有条件）**：Umi 在中文 UI、聊天、表格、低质截图上的收益足够大，值得进入全量重做；但不满足“无差别替换 tesseract”的条件。

建议落地顺序：

1. **路由重做**：中文/表格/低质图走 Umi；代码/终端图保留 tesseract，或 Umi 中文 + tesseract 双结果融合。
2. **不覆盖旧数据**：输出到 `ocr_umi/`，保留现有 `ocr/`；全量后抽 30–50 张人工复核，再决定是否切换。
3. **记录可复现信息**：每份 OCR 文件头写引擎、版本、模型、`limit_side_len`、parser、生成时间；增量缓存按图片内容哈希，不再按 mtime，避免 `git checkout` 后全量误跑。
4. **同步修检索**：`tools/search.ps1` 增加 NFKC + 合并中文间空格的查询归一化；OCR 文本也做同样归一化后再建检索层。
5. **全量执行**：3,465 张单并发约 75–125 分钟；建议 2–4 并发、失败重试、断点续跑。Umi 服务需先启动并监听 `127.0.0.1:1224`。
